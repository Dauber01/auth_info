# API Design Conventions

Follow the repository's AGENTS.md and existing Proto contracts. Extend existing
HTTP and gRPC conventions instead of introducing a second response envelope.

## URL Naming

- Use plural nouns for resources: `/users`, `/orders`, `/products`
- Use kebab-case for multi-word resources: `/order-items`, `/user-profiles`
- Nested resources for belongsTo relationships: `/users/{id}/orders`
- Maximum two levels of nesting; beyond that, use query parameters
- Use query parameters for filtering: `/orders?status=active&limit=20`

## Contracts and Responses

- Define business requests and replies in `api/proto/`; regenerate them with
  `make proto`. Do not edit generated Go files or invent parallel handler structs.
- JSON success replies use `code` and `message`; data-bearing replies add the
  `data` field defined by their specific Proto contract. Operation-only replies
  use `OperationReply`, for example `{"code": 200, "message": "created successfully"}`.
- Use `httpx.WriteOperationReply` for operation-only success responses. Return
  errors through `httpx.WriteError` so the global middleware owns rendering and
  logging. Verify its current error envelope before documenting an endpoint;
  do not assume error bodies are the same as success replies.
- File endpoints return the generated bytes with the appropriate content type
  and disposition; do not wrap PDF or Word bytes in a JSON success envelope.

## HTTP Status Codes

- 200: 成功返回数据
- Existing create/update/delete handlers use 200 with an operation reply.
  Preserve existing status codes unless a contract change is explicitly requested.
- 400: 请求参数错误
- 401: 未认证
- 403: 无权限
- 404: 资源不存在
- 409: 资源冲突，例如重复的字典编码或用户名
- 500: 服务器内部错误

## Authentication

- Protected routes use JWT authentication followed by Casbin authorization.
- Public login and registration routes are registered outside the protected
  router group. Express public access through route registration and ordinary
  comments; there is no special public-access annotation parser.
- Token format: `Authorization: Bearer <jwt-token>`

## Validation and Errors

- Define validation with `buf.validate` in Proto files and use the existing
  `httpx` binding and validation helpers, including path-ID validation.
- The business layer returns stable `apperr` codes. Preserve underlying errors
  with wrapping and leave HTTP/gRPC mapping to the existing boundary code.
- Add failure-path tests for authentication and authorization changes, following
  AGENTS.md. Keep business logic out of handlers and persistence details out of biz.

## Versioning

- API version in URL path: `/api/v1/users`
- Breaking changes require new version
